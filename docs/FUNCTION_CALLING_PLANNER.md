# One-shot Function Calling Planner

This variant adds one native Qwen `tools` / `message.tool_calls` planning request
to the LangGraph/Web entry point. It is not ReAct, a tool-result replanning loop,
or a deployment change. The legacy `agent.run()` / `FinancialAgentRunner` is
unchanged. Rule mode remains the default.

## Configuration

Explicit `LangGraphFinancialAgent` constructor options take precedence over
`base.config.config`, then defaults. An explicitly injected planner wins over
the mode factory. Project `.env` still overrides shell variables through the
existing dotenv behavior. No real credentials or global model settings change.

| Environment | Default | Constructor option |
|---|---|---|
| AGENT_PLANNER_MODE | rule | planner_mode |
| AGENT_PLANNER_MODEL | existing LLM_MODEL | planner_model |
| AGENT_PLANNER_TIMEOUT | 30 seconds | planner_timeout |
| AGENT_PLANNER_FALLBACK_TO_RULE | false | planner_fallback_to_rule |
| AGENT_PLANNER_MAX_CALLS | 8 | planner_max_calls |

The FC client uses the existing DASHSCOPE_API_KEY and DASHSCOPE_BASE_URL without
creating IntegratedQASystem. Client injection is supported. SDK retries are
explicitly disabled; output is limited to 4096 tokens, with non-thinking,
non-streaming native tool calls and `tool_choice=auto`. `parallel_tool_calls`
only permits multiple model calls in one response; actual tools remain serial.

## Arguments and execution

- financial_rag: `{query}`; at most one call, potentially multiple targets.
- market_mcp: `{company_name?, ticker?}`; at least one identifier, multiple calls.
- news_mcp: `{query, company_name?, ticker?, max_results?}`; at least one
  identifier, result count 1-10, multiple calls.
- calculator: `{operation, ...operation-specific inputs}`; at most one call.
  Operations/inputs match CalculatorTool, including a whitelisted AST expression.

The complete plan is validated before execution. Unknown keys/tools, duplicate
IDs, conflicting identifiers, ungrounded targets/periods, unsafe or ungrounded
arithmetic, repeated singleton tools, and excess total calls reject the plan.
No valid subset is executed after another call fails validation. Model-provided
arguments are preserved as `validated_arguments` and passed to actual execution;
FC calculator requests are never regenerated by the rule query parser.

Each call and result retain a call_id. `required_tools` and `executed_tools` are
only category-level compatibility fields. Multiple market/news calls are not
collapsed by name. Actual execution order remains Financial RAG, Market, News,
Calculator, followed by existing aggregation, synthesis and guardrail.

Model-generated RAG text is checked against recognized companies, periods,
metric aliases, selected accounting qualifiers and numeric constraints. This is
a conservative validator, not proof of semantic equivalence of arbitrary prose.
Operand grounding likewise does not prove correct arithmetic operation selection.
Calculations requiring an unknown future tool result are rejected; existing
financial growth calculations can still be delegated to Financial RAG.

## Context and shared safety

FC receives original query, explicit companies/periods, separate prior session
companies/periods, bounded previous query, and explicitly saved preferences.
Preferences do not authorize adding targets. Rule mode retains its original
query + has_company_context interface. A missing-company pronoun is handled by
shared safety before any model request, and is recorded as `shared_safety`, not
FC success. A multi-company pronoun cannot silently select one inherited target.

Every turn clears planned_calls, call_results, metadata, no_tool_response and
temporary output state. Resetting period_clarification fixes a pre-existing
shared-state bug in both arms. Any gain from that fix is not attributed to FC.

Normal no-tool responses are distinct from API errors, empty responses,
truncation and invalid plans. Model prose is not used as an ungrounded financial
answer: the existing safe response path is used. Optional deployment fallback
selects one complete rule plan and records requested/effective mode, cause,
original FC status and request/usage. Strict A/B disables fallback.

## Validation and request budget

Offline commands (no production stores or providers):

```bash
python -B -m unittest tests.test_function_calling_planner tests.test_planner_ab \
  tests.test_real_user_agent_regression tests.test_agent_final \
  tests.test_calculator_tool tests.test_agent_streaming tests.test_agent_mcp tests.test_agent_mvp
python -B -m evaluations.run_real_user_paraphrase_regression run
```

Real FC-only smoke and known-set A/B (explicit paid-call authorization required):

```bash
python -B -m evaluations.run_planner_ab smoke --planner-mode function_calling \
  --output evaluations/planner_fc_review/smoke.json \
  --budget-file evaluations/planner_fc_review/request_budget.json \
  --request-limit 10 --total-request-limit 160 --confirm-model-calls
python -B -m evaluations.run_planner_ab run --planner-mode rule \
  --output evaluations/planner_fc_review/rule.json
python -B -m evaluations.run_planner_ab run --planner-mode function_calling \
  --output evaluations/planner_fc_review/function_calling.json \
  --budget-file evaluations/planner_fc_review/request_budget.json \
  --request-limit 150 --total-request-limit 160 --confirm-model-calls
```

Use the same budget ledger for the entire authorized experiment. Requests are
reserved and fsynced before sending, including attempts interrupted by process
termination. Output files cannot be overwritten. There is no automatic replay
or model retry. Do not delete a ledger to bypass a budget.

The eight smoke inputs cover four single tools, two composite paths and repeated
Market/News targets. No RAG generation, MCP process, provider or business memory
is used; downstream tools and synthesis are fixed fixtures.

Both 150-turn arms use identical question-derived initial context snapshots,
without feeding expected labels to the model. Each row gets a fresh in-memory
graph. This does not demonstrate real sequential Redis memory recovery. The
dataset is an existing known regression set, not a new unseen holdout.

Results include the old raw v1 and corrected v1.1 metrics with unchanged scoring
functions, plus separate planning diagnostics: actual request count, usage,
latency, rejection/fallback, call validation and exact argument delivery.
Composite planning is exact planned-tool set equality on the composite category.
Target coverage is the union of observed company targets against existing
company labels. Repeated-tool target coverage is evaluated only for labeled
single-category multi-company Market/News cases. Full Argument Accuracy is null:
there are no independently audited complete argument labels. Argument Validity
must never be advertised as Argument Accuracy. Raw tool results here are fixture
execution results and cannot be advertised as live provider availability.

The saved protocol includes code hashes, dataset/context hashes and base commit
f2cd985. Historic retrieval results (bcf70ae / 4dbb304) and Agent results
(a68f1db / 7204eca) remain separate artifacts; query planning changes do not
inherit their answer-quality claims. No benchmark prompt tuning or automatic
reruns are performed.
